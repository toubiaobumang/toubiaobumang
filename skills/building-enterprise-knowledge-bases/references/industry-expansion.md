# 行业扩展规则

只在识别出企业行业或用户明确指定行业后应用对应专业档案。通用骨架保持不变，行业档案只增加实体、字段、台账和匹配规则。

# 建筑 / 工程 / 招投标

## 专业目标：投标匹配就绪

本行业不能停留在“资料已经分类”。完成后应能把新的招标条件转成结构化查询，并反查企业已有资质、人员、业绩、信用奖项、财务保险、设备和技术方案。

初始化建议：

```bash
python scripts/initialize_kb.py "<企业知识库根目录>" --profile construction-bidding
```

## 必须维护的专业台账

1. `投标事实索引.csv`：供 AI/匹配模块查询的原子事实层。
2. `企业资质台账.csv`：企业资质类别、专业、等级、编号、有效期和核验来源。
3. `投标人员台账.csv`：注册、职称、安全证、社保/劳动关系、在职状态、可承担角色。
4. `企业业绩台账.csv`：工程类别、专业、金额、规模、时间和业绩证据链。
5. `个人业绩台账.csv`：人员在具体项目中的角色、项目指标和证明材料。
6. `信用奖项台账.csv`：信用评价、奖项、荣誉、认证等。
7. `财务税务保险台账.csv`：年度/期间、指标、证明文件和有效性。
8. `设备资源台账.csv`：设备型号、规格、数量、权属、状态和证明。
9. `技术方案索引.csv`：历史方案按专业、工程类别、工序/主题和适用场景索引。

## 投标事实索引：一行一个事实

一行只表达一个可比较事实，例如：

```text
PERF-001 | 企业业绩 | XX冷链项目 | 合同金额 | 8200 | 万元
PERF-001 | 企业业绩 | XX冷链项目 | 建筑面积 | 18600 | ㎡
PERF-001 | 企业业绩 | XX冷链项目 | 工程类别 | 公共建筑 | 
P-001    | 人员     | 张三       | 注册专业 | 建筑工程 | 
```

规则：

- 保留 `原始值`，另写 `标准值`，禁止覆盖原文。
- 日期统一 `YYYY-MM-DD`；原文只有年份/月时不得补造具体日期。
- 金额和工程量必须记录单位；无明确单位时保持待核验。
- 同一对象的多项专业、奖项、证书等应拆成多条事实，不把列表塞进一个无法比较的字段。
- 每条事实都记录来源文件、正式归档路径、来源定位、状态和最后核验日期。

## 企业资质

至少抽取：

- 资质名称、类别、专业、等级；
- 证书编号、发证机关；
- 生效日期、到期日期；
- 当前状态；
- 正式证书路径；
- 官方核验来源（如资料中存在或用户授权核验）；
- 最后核验日期。

不要把营业执照经营范围当成施工/设计资质证明。

## 投标人员

人员不是一张证书，而是以下关系集合：

`人员 → 注册证 → 职称 → 安全证 → 社保/劳动关系 → 在职状态 → 项目经历`

至少可查询：注册类别、专业、等级、编号、有效期；职称专业和等级；安全证类型、编号、有效期；社保覆盖期间；可承担角色；个人业绩。

缺任一关键条件时，不得仅凭“有这个人”标记完整满足。

## 企业业绩

业绩必须为可筛选结构，而不是一个“金额/规模”摘要字段。至少抽取：

- 项目名称、建设单位、项目地点；
- 工程类别、专业类别、项目标签；
- 合同金额及单位；
- 建筑面积、长度、高度、跨度、容量等可识别指标及单位；
- 中标、合同、开工、竣工日期；
- 项目经理、技术负责人；
- 中标通知书、合同、验收材料、官方查询证明等路径；
- 证据完整度、事实状态、最后核验日期。

仅抽取资料中明确出现的指标。招标条件要求的指标在知识库中缺失时应返回“待核验/未发现”，不能估算。

## 个人业绩

个人业绩必须绑定“人员 + 项目 + 角色 + 时间 + 证据”。项目属于企业，不等于任意员工都拥有该项目个人业绩。

## 信用、奖项、财务、设备、方案

这些对象同样要拆成可比较字段，并保留适用对象、适用区域、日期/有效期、证明材料和状态。技术方案主要用于检索复用，不因历史项目存在某方案就推断当前项目可以直接采用。

## 匹配接口

读取 `references/bid-matching-contract.md`。知识库负责“我有什么”，不负责猜测招标条件；招标条件应由解标模块结构化后再查询。

# 其他行业

制造、软件、咨询、贸易等行业继续使用通用实体模型并按业务增加专业台账。不要把建筑投标字段强加给无关企业。

# 行业不明确

不要猜。先创建通用知识库；行业确认后再追加专业档案，不能为了补齐模板虚构实体或字段值。
