# 企业知识实体模型

## 原则

按“业务对象 + 原子事实 + 证据关系”建知识，而不是按文件格式建知识。文件是证据载体；企业、人员、资质、项目、业绩、合同、客户等才是知识对象。

## 通用实体

| 实体 | 典型字段 | 常见关系 |
|---|---|---|
| 企业 | 名称、统一标识、行业、地址、主营业务 | 人员、资质、项目、产品 |
| 人员 | 姓名、岗位、专业、状态 | 证书、社保、项目、个人业绩 |
| 客户/供应商 | 名称、行业、区域、状态 | 合同、项目、案例 |
| 项目 | 名称、客户、时间、金额、规模、状态 | 合同、人员、成果、业绩 |
| 资质/证书 | 名称、编号、专业、等级、有效期 | 企业、人员、投标条件 |
| 合同 | 编号、双方、金额、周期、范围 | 项目、客户、业绩 |
| 产品/服务 | 名称、型号/版本、能力/参数 | 客户、项目、案例 |
| 知识主题 | 名称、适用范围、关键结论 | 项目、方案、标准、来源 |

## 建筑投标专业实体

在 `construction-bidding` 档案中增加：

- 企业资质；
- 投标人员资格组合；
- 企业业绩；
- 个人业绩；
- 信用/奖项/荣誉；
- 财务/税务/保险事实；
- 设备资源；
- 技术方案资产；
- 招标条件（由下游解标输入，不作为企业自身事实）。

## 三层表达

### 1. 实体层

回答“谁/什么”：张三、XX项目、某资质证书。

### 2. 原子事实层

回答“对象的某个可比较属性是什么”：

`XX项目 → 合同金额 → 8200万元`

`张三 → 注册专业 → 建筑工程`

每条事实单独有状态和来源。

### 3. 证据层

回答“为什么可以相信”：原始文件、正式路径、页码/章节、版本、有效期、核验时间。

## 实体页最小字段

每个重要实体页至少应有：`entity_id`、名称、实体类型、当前状态、已确认事实、待核验事项、关联实体、原始证据、最近更新时间。

## 关系规则

1. 只有来源支持时才建立关系。
2. 关系必须能回答“依据是什么”。
3. 多源冲突必须保留，不静默覆盖。
4. 关系可标记 `已确认 / 待核验 / 历史 / 失效 / 版本冲突`。
5. 不为图谱完整性创建推测边。
6. 企业业绩与个人业绩是不同实体关系，禁止自动继承。
7. 资格组合（如“一级建造师 + B证 + 社保”）是匹配时计算的组合，不要伪造为一张不存在的证书。
